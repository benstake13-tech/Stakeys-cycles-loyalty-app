## What shipped (commit `80c2e14`, cherry-picked `-x` to `staff-terminal` `5bfa199` + `main-website` `7d22cc9`)
The native release build was produced **unsigned** (`app-customer-release-unsigned.apk`) — the
one piece the 2026-10-07 native session explicitly deferred — so it could not be installed or
uploaded to Play. Now signed with a project keystore.

- `android/app/build.gradle`: reads a **git-ignored** `android/keystore.properties` (when
  present) into a `signingConfig` applied to the `release` build type. When the file is absent
  (CI, fresh clone, other dev) the release build simply stays unsigned and the repo still
  builds — so **no secret lives in git** and `check:parity` is unaffected.
- `scripts/gen-keystore.sh`: generates `android/stakeys-release.jks` + `keystore.properties`
  (RSA 2048, 10000-day validity, alias `stakeys`, DN `CN=Stakey's Cycles…, L=Salford, C=GB`).
  Refuses to overwrite an existing keystore; accepts `STORE_PASSWORD` for non-interactive use.
- `android/.gitignore`: now excludes `*.jks`, `*.keystore`, `keystore.properties`.
- `NATIVE_APPS.md`: new "Release signing" section (key stability, backup, Play App Signing note).

Verified: `apksigner verify` → v1+v2 schemes, 1 signer, cert DN = Stakey's Cycles. Debug
`assembleCustomerDebug` still builds. `bundleStaffRelease` → signed `.aab` (`jar verified`).
`scripts/build-apps.sh --only customer --release` → `preview/apps/stakeys-customer.apk` (signed,

## Native customer sign-in investigation (2026-10-12, "cannot sign in to the native Android app")
- **It is NOT a native/Capacitor bug.** Proven via supabase-js against the live project:
  `signInWithPassword` for EVERY profile email (chloelawrence897@, muhammadhamzaiqbal165@,
  groslots@, gsalford4@gmail.com) + the default `Stakeys123!` + `password123` -> all
  `400 invalid_credentials`. The web has the SAME failure; the native report just surfaced it.
  `bridge_diagnostics` still reports HEALTHY (auth_logins=10, profiles_without_login=0) => those
  10 auth.users exist but their passwords match no known value.
- **Real blockers (server-side, need owner + service_role):** (1) `mailer_autoconfirm:false` + dead
  SMTP => signup 500 "Error sending confirmation email"; (2) member auth.users passwords unknown.
  No service_role in this sandbox (no env, no psql, no supabase CLI; anon cannot touch auth.users).
- **App-side defects found (fixable here, they HIDE the real cause):**
  - `loginWithCredentials` (ShopContext ~L2206) maps EVERY non-"not confirmed" error to the literal
    string **"Invalid email or password."** — a 500, a 429, and a network failure all look identical.
  - Customer form has **no "Forgot password?"** though `resetPassword()` exists (its redirectTo
    `/reset-password` has no handler either).
  - Sign-in advertises **"Demo customers (Alex, Maya, Liam) require password: password123"** — those
    profiles DO NOT EXIST. Misleading hint shown to real customers.
  - No custom scheme / App Link in AndroidManifest => an email-confirmation link can never open the app.
- **Correct fix:** owner sets `mailer_autoconfirm=true` (or real SMTP) AND runs
  `select public.link_member_login('<email>','<newpass>','<name>');` per member (or
  `backfill_member_logins`) in the Supabase SQL Editor — same session-14 remediation.
