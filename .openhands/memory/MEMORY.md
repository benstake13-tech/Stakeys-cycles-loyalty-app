# Project Memory — Stakeys Cycles Loyalty App

React 19 + Vite + TS + Supabase loyalty/rewards app for a bike shop.

## Key facts
- `UserProfile` primary key is `uid` (NOT `id`). `CustomerBike` has `category/categoryLabel/brand/model/...`, optional `scrapedData`, `aiIdentification`.
- `addCustomerBike(bike)` adds to the *current user's* garage (`ShopContext.tsx`). `addCustomerBikeForUser(userId, bike)` adds to any user's garage — use this for staff-side flows. Both optimistically update `users`/`currentUser` then persist via `insertCustomerBikeToDb`.
- AI Bike Identifier: `src/components/AiBikeIdentifier.jsx` (uses `useShop`). Vision backend `src/api/visionService.js` uses `@google/genai` structured JSON output. Reads `import.meta.env.VITE_GEMINI_API_KEY`; shows a graceful "not configured" state when unset. Optional `addBike` prop overrides the default persistence (used by staff dossier).
- `SegmentedTabs` / `SegmentedTab` shared component in `src/components/SegmentedTabs.tsx`, used by CustomerPortal + StaffPortal nav.
- Discount-code system (2026-10-03): pure logic in `src/utils/discountService.ts` (`validateDiscountCode`, `computeDiscountAmount`, `findDiscountCode`, `computeSaleTotals`, `roundMoney`, `voucherToDiscountState`, `promotionToDiscountCode`). Types `DiscountCode`/`SaleTransaction`/`SaleDiscountState` in `types/bikeShop.ts`. Persistence `discount_codes` + `counter_sales` in `backendDataService.ts`; context CRUD `discountCodes`/`sales`/`addDiscountCode`/`updateDiscountCode`/`deleteDiscountCode`/`refreshDiscountCodes`/`completeSale`/`recordDiscountUsage`. UI: `DiscountCodesTab.tsx` (staff tab `discount_codes`) + `CounterSaleTab.tsx` (staff tab `till`). The till re-derives the discount via `useMemo` on every basket change (do NOT store a stale `amountOff`). Scanner recognises discount codes when a scan isn't a member.
- `roundMoney` uses the exponential-shift trick (`Number(Math.round(Number(\`${v}e2\`)) + 'e-2')`) because the naive `Math.round(v*100)/100` mis-rounds 1.005 → 1.00.
- Seasonal theme: cross-account via shared Supabase row `app_theme_config(id=1, theme)` (values none|halloween|christmas|easter|cny|valentines), realtime `theme_changes`. UI `StaffThemeSelector.tsx` (StaffPortal); animation `SeasonalThemeCanvas.tsx` (rewritten to an atmospheric "mischief" engine — sky/ground/parallax backdrop/weather + cycling characters doing wheelies, skids, snowball fights, falling off laughing). Mounted in `App.tsx` as z-0 sibling of content (z-10). No `SEASONS` second export (breaks Fast Refresh).
- Counter sale vouchers: `SaleTransaction.discountSource` ('discount_code'|'voucher'|'promotion') + `discountVoucherId`; `processSale` consumes EITHER `recordDiscountUsage` OR `redeemServiceVoucher`, never both (double-count fix).
- `tsc --noEmit` is CLEAN (0 errors) and `vite build` passes.

- Balance diagnostic + profile-write root cause (session 10): the live `profiles` table HAS every balance column (stamps/completed_cards/merit_points/last_spin_date/last_spun_at/last_stamped_at) and reads fine. The real fault was the WRITE: `updateUserProfileInDb` used `upsert(payload, {onConflict:'id'})`, and `profiles.display_name` is **NOT NULL** on the live DB. PostgREST builds an INSERT candidate for an upsert even when the conflict target row exists; with `display_name` omitted that candidate violates 23502 *before* conflict resolution, so EVERY profile write (stamps, tickets, merit_points, last_stamped_at, last_spun_at, last_spin_date) silently failed → addStamp/spin/staff-adjust/cooldown-reset were all no-ops. Fix: `updateUserProfileInDb` now PATCHes (`update(payload).eq('id',userId).select('id')`) and, if no row matched, calls `ensureProfileRowInDb` then retries. The diagnostic's probe was also rewritten to snapshot→write→verify→restore a REAL profile (`planBalanceProbe`), because the old synthetic `__stakeys_diag__profile-*` id could never exercise a real write. Lesson: **a partial upsert against a table with any other NOT NULL column without a default is always rejected; PATCH existing rows instead.**
- Cooldown system (session 10): `last_spun_at` (fetch helper's primary) and legacy `last_spin_date` must be written together or the weekly 1-spin limit is bypassed — `updateUserProfileInDb` now mirrors `last_spun_at`→`last_spin_date` (and clears both together). `updateCustomerPoints` accepted `resetDailyRateLimit`/`resetSpinCooldown` but cleared them only in local state (as `undefined`) and never persisted them, so staff overrides reverted on refresh; now sent as explicit `null` (local state uses `null` too). `resetUserSpinCooldown` uses the same write path.
- Data plane is Supabase-only (session 10, verified): every table write/read goes through `getSupabaseClient()`; `firebase` + `pocketbase` remain in package.json but Firebase is used only for pure helpers (`generateMembershipNumber`, `generateBarcodeValue`, `canCustomerReceiveStampToday` — no Firestore reads/writes, no calls to `registerCustomer`/`addStampToCustomer`/`spinWheel`) and PocketBase only as a configurable health-check target (`updatePocketBaseTargetUrl`). Do not reintroduce a second data plane.
- Counter-sale lifecycle (session 10): `updateCounterSaleInDb` used the SAME partial-upsert bug as profiles — `counter_sales.items` is NOT NULL on the live DB, so a partial upsert built an INSERT candidate that PostgREST rejected with 23502 before conflict resolution, and the "Quote → approve a counter sale" diagnostic always showed `status = completed (expected approved)`. Now it reads the row, builds a merge-aware `saleLifecyclePatch(existing, updates)` (so approving keeps the quote already sent — a blind `saleLifecycleColumns(updates)` nulled it), and PATCHes `update(payload).eq('id')`. The diagnostic hint "counter_sales is missing quote/approval lifecycle columns" was WRONG — all lifecycle columns exist live; corrected the hint. Verified live: insert → PATCH quote → PATCH approve → read gives status=approved with quoted_amount/quote_note intact.
- Rule of thumb (session 10): on the live DB, `profiles.display_name` and `counter_sales.items` are NOT NULL. ANY `update*InDb` helper that upserts a partial payload will silently fail with 23502. Use PATCH for updates; reserve upsert for inserts that carry the full row. Other tables' partial upserts (app_settings id=1, prize_wheels/draws, discount_codes, staff_members, promotions, service_vouchers) still use upsert — safe only because their other columns are nullable/defaulted, but audit before adding NOT NULL columns.
