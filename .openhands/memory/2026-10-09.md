## Follow-up (2026-10-09) — "can't create a plan / send does nothing" is an OpenHands bug, not this app
User asked to "fix this issue". Investigated: the Stakeys app has NO plan feature
(grep of src for "plan"/planMode/create-plan only hits weather copy + a
planBalanceProbe variable), and the submit-button testid in the report is an
OpenHands UI testid. This is upstream OpenHands/OpenHands#18202 "[Bug]: Send stays
disabled after branching from a user message with prefilled text" (open,
priority:medium, ready-for-dev). Root cause (from the issue triage): the composer
is contentEditable; programmatic prefill (branch-from-message draft restore,
empty-state suggestion chips, + > Macros, header Git-actions Pull) writes
element.textContent WITHOUT dispatching an input event, so CustomChatInput's
canSubmit stays false and Send stays disabled until a character is typed.
Fix PRs already open: #18203 (draft) and #18226 — both unmerged/blocked.
Workaround for the user: after the text is prefilled, press Enter (Enter-to-send
works) or type-and-delete one character; a full reload of a branch also restores
the draft but still needs a keystroke. The OpenHands frontend source is NOT in this
sandbox (only /usr/local/bin/openhands-agent-server + the VS Code server binary),
so the product bug cannot be patched from here.

## Session (2026-10-09) — Gemini key wiring + AI truncation fix
- The app's AI features (AI Bike Identifier, Shop Assistant, booking-notes
  translation) read `import.meta.env.VITE_GEMINI_API_KEY` at build time — it is a
  CLIENT-SIDE Gemini key, so it IS inlined into the public bundle by design
  (`grep AQ.Ab8RN6 dist/` finds it). `.env.local` is git-ignored; `.env.example`
  is the committed template.
- Env `$GEMINI_API_KEY` (secret store) is a DIFFERENT, DEPLETED key: every model
  returns HTTP 402 "prepayment credits are depleted". The key the user pasted
  (`AQ.Ab8RN6JcV-…`, 53 chars, starts `AQ.`, from AI Studio) is a free-tier key
  that WORKS: `gemini-flash-latest` and `gemini-3.8-flash` return HTTP 200.
  `gemini-2.5-*` return 404 "no longer available to new users" for this key — so
  the repo's `gemini-flash-latest` default alias is the correct choice.
- ROOT-CAUSE FIX (real bug, independent of which key): Gemini **3.x** models spend
  hidden "thinking" tokens out of `maxOutputTokens`. The app capped translation
  at 400 and assistant at 400, so replies were silently TRUNCATED mid-sentence.
  Fix: shared `NO_THINKING = { thinkingConfig: { thinkingBudget: 0 } }` in
  `src/api/geminiModel.ts`, spread into the translation + assistant configs
  (assistant budget bumped 400→800). Re-verify by running a translate call.
- GOTCHA: once `.env.local` holds a real key, Vitest loads it, so
  `booking_translation.test.ts` "unconfigured" test made a LIVE network call and
  failed non-deterministically. Fixed with `vi.stubEnv('VITE_GEMINI_API_KEY','')`
  in a `beforeEach` + `unstubAllEnvs()` afterEach — any test that exercises a
  Gemini service must pin the key or it will hit the network.
- Key must also be set in the Vercel project (Production+Preview) since it is a
  build-time VITE_ var; a git push alone does not update the live key. User must
  rotate the AI Studio key because it was pasted into the chat.
- Commit staff-terminal 96ee67e, cherry-picked to both branches; gate green
  (99 files / 734 tests); pushed all three (customer-app fdc9272 / main-website ecd09ae).
